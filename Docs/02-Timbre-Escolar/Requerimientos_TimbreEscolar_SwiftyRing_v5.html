Cambios frente a la versión 4.0

Al proyecto de grado se sumó un segundo módulo, Control Baños SS, desarrollado por otro equipo de aprendices de la misma institución. Los dos módulos se entregan sobre una misma aplicación móvil y una misma base de datos, pero se desarrollan y despliegan por separado.

Lo que no cambió Ninguna funcionalidad del Sistema de Timbre Escolar. Las 17 tablas del modelo de datos, los 43 requerimientos funcionales originales y el módulo físico ESP32 quedan exactamente igual. Los cambios de esta versión son de frontera: definen qué puede y qué no puede hacer un módulo ajeno que comparte infraestructura.
Qué cambióCómo estaba (v4.0)Cómo queda (v5.0)
Rol del backendAutenticaba únicamente a su propia appAdemás actúa como servidor de identidad de la aplicación institucional
Firma de tokensHMAC-SHA512, llave única compartidaRS256: llave privada firma, llave pública verifica
Claims del JWTsub, exp, rolSe agregan iss, aud, iat, nombre, email
Base de datosBase propia y exclusivaBase compartida; el timbre conserva el schema public intacto
Permisos de PostgreSQLUn solo rol con acceso totalSe agrega proyectobanos con solo lectura sobre dos tablas
Estructura del códigolib/features/…lib/core/ + lib/modules/, módulo ajeno eliminable
Compatibilidad iOSiOS 14+iOS 15+ — impuesto por Xcode 27, que no admite objetivos por debajo de 15.0
Totales43 RF · 9 RNF48 RF · 13 RNF

Las condiciones exactas de la frontera entre los dos módulos están en Docs/04-Integracion/Contrato_Integracion_Timbre_ControlBanos.md.

01 · Visión general
01

Visión general

Sistema integrado de control de timbre escolar compuesto por una aplicación móvil Flutter y un módulo físico basado en ESP32. El backend es propio: Vapor + PostgreSQL alojado en un servidor dedicado, lo que garantiza control total sobre los datos, independencia de plataformas externas y escalabilidad a largo plazo. Las notificaciones push se entregan mediante FCM (Firebase Cloud Messaging) únicamente como canal de entrega, sin depender de ningún otro servicio de Firebase.

Swifty.Devs
02 · Arquitectura del sistema
02

Arquitectura del sistema

El backend Vapor es el centro del sistema: la app y el módulo ESP32 se comunican con él, guarda todo en PostgreSQL y despacha las notificaciones a los profesores por FCM.

El módulo ESP32 llama a Vapor cada vez que el timbre suena —automático, manual o sísmico— y opera de forma autónoma aunque pierda la conexión.

Requerimientos funcionales

3.1 · Gestión de usuarios y autenticación

IDRequerimiento
RF-01El sistema contará con autenticación propia mediante JWT (JSON Web Tokens) gestionada desde el backend Vapor.
RF-02Existirá una cuenta de Administrador Principal (Doña Andrea) creada en la inicialización del sistema, no eliminable.
RF-03El administrador principal podrá crear, editar, suspender y eliminar usuarios secundarios.
RF-04El sistema manejará tres roles: Administrador, Operador y Profesor.
RF-05Los operadores podrán consultar horarios y activar el timbre manual, pero no modificar horarios ni gestionar usuarios.
RF-06El administrador podrá asignar y revocar permisos individuales por usuario.

3.2 · Módulo de horarios

IDRequerimiento
RF-07El sistema permitirá definir un horario habitual semanal con múltiples timbres por día.
RF-08Cada timbre tendrá: hora, días activos (L-S), etiqueta descriptiva (ej. Inicio de clases) y duración del sonido.
RF-09El administrador podrá crear, editar y eliminar timbres del horario habitual.
RF-10El sistema soportará horarios especiales que suspenden temporalmente el horario habitual.
RF-11Al activar un horario especial, se habilitará un date picker para definir el rango de días de vigencia.
RF-12Al vencer el rango del horario especial, el sistema retomará automáticamente el horario habitual.
RF-13Solo el administrador podrá activar, modificar y desactivar horarios especiales.

3.3 · Timbre manual

IDRequerimiento
RF-14La app contará con un botón de timbre manual visible en la pantalla principal.
RF-15El módulo ESP32 contará con un botón físico de timbre manual.
RF-16Ambos botones ejecutarán el timbre de forma inmediata, independientemente del horario activo.
RF-17Cada activación manual quedará registrada en PostgreSQL con usuario, timestamp y origen (app / físico).

3.4 · Módulo de detección de sismos

IDRequerimiento
RF-18El ESP32 contará con un acelerómetro (MPU-6050) para detección de vibraciones sísmicas.
RF-19El algoritmo de detección deberá distinguir entre sismos y vibraciones de vehículos, usando análisis de frecuencia y duración de la vibración.
RF-20Un evento sísmico confirmado enviará una notificación push FCM al dispositivo del administrador.
RF-21La notificación incluirá: hora del evento, intensidad estimada (en g) y duración de la vibración.
RF-22Al confirmarse un evento sísmico, el módulo ESP32 activará el timbre de forma inmediata y autónoma. Simultáneamente Vapor enviará la notificación push al administrador como registro del evento.
RF-23El historial de eventos sísmicos detectados será consultable desde la app.

3.5 · Pantalla OLED en módulo físico

IDRequerimiento
RF-24El módulo incluirá una pantalla OLED de 1.3" (SH1106).
RF-25La pantalla mostrará en tiempo real: hora actual, nombre del próximo timbre y tiempo restante.
RF-26Al activarse el timbre, la pantalla mostrará un indicador visual de timbre activo.
RF-27Si no hay conexión a internet, la pantalla indicará el modo offline con un ícono visible.

3.6 · Operación offline

IDRequerimiento
RF-28El ESP32 almacenará localmente el horario activo en memoria flash (SPIFFS / LittleFS).
RF-29La app Flutter utilizará caché local para permitir consulta y edición de horarios sin conexión.
RF-30Los cambios realizados offline se sincronizarán automáticamente con el backend al recuperar conectividad.
RF-31El módulo ESP32 operará el timbre automático de forma autónoma aunque pierda conexión al servidor.

3.7 · Módulo de profesores y notificaciones de clase Nuevo en v2.0

IDRequerimiento
RF-32Cada profesor tendrá un perfil en el sistema con: nombre, correo, materia(s) que dicta y token FCM de su dispositivo.
RF-33El administrador podrá crear, editar y eliminar perfiles de profesores desde la app.
RF-34Cada profesor tendrá un horario semanal asignado con entradas que incluyen: día, hora de inicio, hora de fin, materia y salón.
RF-35El administrador podrá cargar y modificar el horario semanal de cada profesor desde la app.
RF-36Al activarse el timbre (automático, manual o sísmico), Vapor consultará qué clase corresponde a continuación para cada profesor según su horario en PostgreSQL.
RF-37Se enviará una notificación push FCM personalizada a cada profesor con: hora de la próxima clase, materia y salón al que debe dirigirse.
RF-38Si un profesor no tiene clase en el siguiente período, no recibirá notificación.
RF-39Los profesores tendrán acceso a la app con rol Profesor, diferente al Administrador y al Operador.
RF-40La app en modo Profesor mostrará el horario semanal completo del profesor autenticado.
RF-41La clase en curso se resaltará visualmente con un indicador de color y etiqueta En curso.
RF-42La próxima clase se resaltará con un indicador secundario y etiqueta Próxima.
RF-43El horario del profesor se actualizará en tiempo real si el administrador realiza cambios durante el día.

3.8 · Servidor de identidad para módulos externos Nuevo en v5.0

Estos requerimientos no describen funcionalidad que el docente vea en pantalla. Describen lo que el backend debe ofrecer para que otro módulo de la aplicación institucional autentique usuarios sin acceder nunca a las credenciales, de modo que el docente use un solo usuario y una sola contraseña para toda la aplicación.

IDRequerimiento
RF-44El backend firmará los tokens JWT con el algoritmo RS256, de modo que la llave de verificación pueda entregarse a terceros sin permitirles emitir tokens.
RF-45El token incluirá los claims sub, exp, iat, rol, nombre, email, iss (emisor) y aud (audiencias autorizadas).
RF-46El backend expondrá la llave pública de verificación en el endpoint público /.well-known/jwks.json.
RF-47El backend expondrá un endpoint de solo lectura GET /api/profesores, accesible con rol Administrador, con la lista de docentes activos.
RF-48Ningún módulo externo podrá crear, modificar ni eliminar registros del Sistema de Timbre Escolar a través de la API. La superficie expuesta es exclusivamente de lectura.
Por qué RS256 y no HMAC Con HMAC la llave que firma y la que verifica son la misma: entregarla para que otro módulo valide tokens le permitiría también fabricarlos, incluidos tokens con rol Administrador. Con RS256 la llave privada se queda en el servidor del timbre y solo se publica la pública. El módulo externo puede comprobar que un token es auténtico, pero no puede crear uno.

Requerimientos no funcionales

IDRequerimiento
RNF-01La app usará los colores institucionales del colegio como paleta principal.
RNF-02La interfaz seguirá los lineamientos de Material Design 3.
RNF-03La app debe ser compatible con Android 8.0+ e iOS 15+.
RNF-04El tiempo de respuesta entre comando de la app y activación del timbre físico no debe superar 2 segundos con conexión estable.
RNF-05El envío de notificaciones FCM a todos los profesores debe completarse en menos de 5 segundos desde la activación del timbre.
RNF-06Toda comunicación entre la app y el backend usará HTTPS con certificado SSL válido.
RNF-07Las contraseñas se almacenarán en PostgreSQL con hash bcrypt. Nunca en texto plano.
RNF-08La autenticación se realizará mediante JWT con tiempo de expiración configurable.
RNF-09El código Flutter seguirá arquitectura Clean Architecture con separación por capas (data / domain / presentation).
RNF-10Autonomía. El Sistema de Timbre Escolar no dependerá en ningún punto de otro módulo de la aplicación institucional: debe compilar, migrar y operar aunque los demás módulos se eliminen por completo.Nuevo
RNF-11Aislamiento de datos. Ningún rol de base de datos ajeno al Sistema de Timbre Escolar tendrá permisos de escritura sobre el schema public. La restricción se aplicará con GRANT/REVOKE en PostgreSQL, no por convención entre equipos.Nuevo
RNF-12Modularidad del código. La app se organizará en lib/core/ (compartido) y lib/modules/<módulo>/. Ningún archivo de core/ ni de modules/timbre_escolar/ podrá importar código de otro módulo.Nuevo
RNF-13Custodia de la llave privada. La llave privada de firma RS256 residirá exclusivamente en el servidor del Sistema de Timbre Escolar, fuera del control de versiones. Solo se distribuye la llave pública.Nuevo

Prueba de aislamiento

RNF-10 y RNF-12 no son declaraciones de intención: se verifican con una prueba concreta antes de cada entrega, sobre una rama descartable.

App móvil

FrameworkFlutter (Dart)
State managementRiverpod / Bloc
Caché localHive / Isar

Backend

FrameworkVapor (Swift)
Base de datosPostgreSQL
ORMFluent (fluent-postgres-driver)
AutenticaciónJWT con vapor/jwt + Bcrypt
ServidorAlmaLinux — Nginx reverse proxy
Dominiohost.swiftydevs.dev

Notificaciones push

ServicioFCM — Firebase Cloud Messaging (solo canal de entrega)
IntegraciónVapor llama directamente a la API HTTP de FCM
Dependencia FirebaseNinguna — solo se usa la Server Key de FCM
